# Whimsy.co

The original four-page design now has a Vite build, a persistent bag, product pages, Supabase account screens, a customer dashboard with order history and a saved bag, and an administrator interface. **Checkout is intentionally disabled**, as requested. No payment gateway, shipping price, free-shipping threshold, or VAT status has been assumed.

## Run locally

Use Node.js 22.16 or newer. On PowerShell, use `npm.cmd` if execution policy blocks `npm.ps1`.

```powershell
npm.cmd ci
npm.cmd run dev
```

Open the printed local address. Without environment configuration, the app explicitly displays a store preview with the original 24 sample products. Guest bags persist in this browser. Accounts and administration require a configured Supabase project; preview mode never fabricates login or orders.

```powershell
npm.cmd test
npm.cmd run build
node scripts/browser-check.mjs
node scripts/check-accounts.mjs
node scripts/check-admin.mjs
node scripts/check-loader.mjs
node scripts/check-shop.mjs
node scripts/check-community.mjs
node scripts/check-supabase.mjs
```

The storefront browser check uses installed Microsoft Edge and a running dev server. Set `TEST_BASE_URL` to check a production preview instead. The account check starts its own server and simulates Supabase HTTP responses; it verifies UI behavior without sending email or accessing a real account. Screenshots are written to ignored `artifacts/`. Database tests run the actual schema and policies in an embedded PostgreSQL engine (PGlite), with a minimal stand-in for Supabase Auth roles and `auth.uid()`. These checks do not replace tests against a live Supabase project.

## Loading experience

The reusable Whimsy loader is connected to real page initialization and authentication requests. Account and dashboard orders use a smaller contextual variant. The initial loading shell is generated by the Vite HTML transform from `src/loader-view.js`; `src/loader.js` releases it as soon as the page renders, including handled errors. There is no minimum display time. The loader browser check gates simulated API responses to verify lifecycle, concurrent tasks, accessibility and reduced-motion behavior without changing live data.

## Connect Supabase

This workspace is connected to **Whimsy.Co** (`czlwrycmzqfvgvohezmx`, `eu-west-1`) through ignored `.env.local` public browser configuration. The available projects and database were inspected before bootstrap: this was the only available project, with no application tables, functions or migration history. `supabase/schemas/001_store.sql` was applied unchanged as remote migration `20261023182535_bootstrap_store`; its exact SQL is saved in `supabase/migrations/20261023182535_bootstrap_store.sql`. The separate seed loaded 24 products with zero stock and disabled checkout. No accounts or administrator memberships were created.

`node scripts/check-supabase.mjs` checks the live public API and the built storefront without creating users or orders. It verifies catalog loading, anonymous denial of customer data, and disabled checkout. Run `npm.cmd run build` first. Live database checks also confirmed that the settings constraint rejects enabling checkout and the authenticated checkout RPC refuses to place an order; those checks ran in a rolled-back transaction.

Local declarative migration generation was attempted but Docker is unavailable, so the initial bootstrap used the connected Supabase migration tool and the recorded remote version was saved locally. The configuration uses the current CLI's `pgdelta` declarative schema path. Future changes should be generated from `supabase/schemas/` after installing Docker; do not reapply the bootstrap.

Supabase advisors reported no warnings or errors after bootstrap. Informational findings were [unused indexes](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index) on the fresh database and [RLS without policies](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) on `private.store_admins`, which intentionally denies client access.

For another empty environment:

1. Create a development Supabase project. Keep production in a separate project.
2. Copy `.env.example` to `.env.local` and set the project's URL and **publishable** key. These values are public browser configuration. Never use a service-role key or secret key. Rebuild after changes.
3. Apply the files in `supabase/schemas/` in numeric order, then `supabase/seed.sql` to a **new, empty** project using the SQL editor for the initial bootstrap. This repository follows a declarative schema workflow; subsequent changes belong in the schema files and generated migrations. Do not reapply the full bootstrap to an existing schema.
4. For CLI-managed environments, apply the existing migrations in order instead of step 3's schema SQL. For subsequent changes, inspect the current CLI's database schema subcommand help, then generate and review a migration from the declarative source before pushing. Seed data is explicitly separate because schema diff tools do not capture data inserts.
5. Seeded inventory starts at **zero** for every product. Set verified quantities, descriptions, product photographs and current prices in the admin interface before launch. The current names, prices and ratings were copied from the original mock catalog and require business review.
6. In Auth settings, set Site URL to your deployment origin and add its full `/account.html` URL to the redirect allowlist. For local development allow `http://127.0.0.1:5173/account.html`. Email confirmation is disabled in local configuration at the owner's request; the hosted project must have its Confirm email switch turned off separately. The signup page handles both immediate sessions and projects that still require confirmation. Configure a production SMTP provider for password reset delivery.
7. Sign up for your store-owner account. If the hosted project still requires confirmation, confirm the email first. In the SQL editor, grant administration using the verified Auth user UUID:

```sql
insert into private.store_admins (user_id) values ('YOUR-VERIFIED-AUTH-USER-UUID');
```

Only trusted SQL/server access can edit this table. User-editable metadata never grants administration. Revoke access by deleting that membership. The private schema must **not** be added to the Data API's exposed schemas.

## Data and access controls

Product editors accept file uploads with a local preview, replacing the former image URL field. JPG, PNG and WebP images up to 5 MB upload on Save to the public `product-images` bucket; only store administrators can upload, list or delete these assets. Migration `20261023202640_add_product_image_uploads` is applied and recorded locally. The product's existing `image_url` stores the resulting public asset URL, so product cards and detail pages use the shared product data without another image system. Saving without a file preserves the existing image. Failed product writes check whether the uploaded image is referenced before removing an unused upload; replaced photographs are retained to avoid breaking other references. Database tests exercise admin-only access and path rules; dashboard browser tests cover previews, invalid formats, upload errors, preserving existing images, new products and save-error cleanup.

The landing page's “Caught in the wild” wall accepts signed-in submissions: photos, outfits, text reviews and pin hauls. Customers see their own submissions under **My shares** on their dashboard and can delete them. Owners use **Community shares** to review all submissions, publish, decline, unpublish or delete them. New submissions are pending; only published content appears publicly. The form asks for a public display name, caption and permission to publish, with JPG/PNG/WebP photos limited to 5 MB. Reviews may omit a photo.

Migration `20261023200654_add_community_shares` is already applied to the connected project, including the private `community` Storage bucket. RLS restricts pending/rejected records and photos to their creator and administrators. Visitors can read approved public fields and request short-lived signed URLs for approved images. Customer email addresses are never part of a public submission. Lists paginate, refresh from the database and escape submitted text. Deletion removes the photo through Storage before deleting the database row. The isolated browser check tests uploads, failure cleanup, persistence, dashboards and publication without live writes. A separate real upload/save/read/cleanup round trip and rolled-back owner publication check passed against the connected project; the temporary test account and content were removed.

The catalogue uses visible Supabase products, real inventory and image URLs. Missing images have an intentional icon fallback; inventory is never inferred from a badge. Keychains are derived from the existing keychain product icon within the pins category; collections and moods use the existing stored values. All visible products render directly below the toolbar, with working search, filters, sorting and product links.

Favourites use the shared store: guests save IDs locally, then merge them into their account on sign-in. Migration `20261023194115_add_favourites` is already applied to the connected project and recorded locally. Its table permits authenticated customers to read, insert and delete only their own favourites; new favourites require a visible product. The catalogue browser check covers guest/account persistence and merge, missing images, visibility, stock, the existing bag and responsive layouts without live writes.

- Public access can read active products and public store settings only.
- Customers can read and update their own profile and bag. They can read only their own orders and order-item snapshots.
- Administrators can manage products and stock, read orders and mark an already paid order fulfilled with a tracking reference. Administrators cannot mark an order paid from the browser.
- Row-level security is enabled on every exposed table. Explicit grants limit operations independently of RLS.
- Guest bag merge uses a retry key, caps quantities at available inventory, and skips unavailable products. Browser bags contain product IDs and quantities only; prices are read from the catalog.
- A bag does not reserve stock. Quantities are checked on writes. Any future checkout must revalidate and reserve inventory in one server transaction.
- The database refuses checkout and prevents setting `checkout_enabled` to true. There is no customer-facing order-creation or payment-status mutation endpoint. Enabling real commerce requires a reviewed backend change, not a client toggle.
- Orders store purchased names and prices separately from the live catalog. Updating a product does not rewrite order history.

## Hosting

`npm.cmd run build` produces `dist/` for static hosting. `.openai/hosting.json` records the associated Sites project. Keep its project ID when updating that Site. Supabase public values are build-time environment variables and must be supplied before building a connected release. Host only `dist/`, never the source directory or `.env`.

## Before accepting real orders

Checkout remains closed until the business confirms a payment gateway, delivery areas and prices, any free-shipping rule, VAT treatment, invoice requirements, final product content and store policies. The former R600 announcement was placeholder copy and has been removed.

The remaining commerce implementation is intentionally deferred: server-priced order creation with stock reservations and expiry, provider-hosted payment, verified and idempotent payment webhooks, cancellation/refund handling, and transactional order/payment/fulfillment emails. Configure production email delivery and test failed payments, duplicate and delayed webhooks, simultaneous purchases of the last item, reservation release, and reconciliation before enabling checkout. No funds can be taken in this version.

The existing contact page's WhatsApp number (`61412345678`), email addresses, social links, response promises and marketing copy came from the supplied site and still need confirmation. The newsletter signup was an unconnected visual mock; it no longer reports a successful subscription. Full legal/privacy/returns text and real business contact details are launch prerequisites.

The live catalog, public API access controls, remote advisors and disabled checkout have been checked against the connected project. Live account signup, email delivery and deployment-specific Auth redirect settings still require validation before launch. See the current [Supabase Auth documentation](https://supabase.com/docs/guides/auth), [RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security), and [declarative schemas guide](https://supabase.com/docs/guides/local-development/declarative-database-schemas) for configuration details.
